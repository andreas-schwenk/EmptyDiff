EmptyDiff

EmptyDiff checks submissions in programming lab courses automatically. Students upload their files and see the result right away. For each lab, lecturers write a testbench, a short automatic test, see all submissions and keep the credit list. The check runs in a sandbox. The system runs on Linux (recommended: Debian or Ubuntu) and currently checks Octave and MATLAB files (.m). It is free software under the GPLv3.

What it is for

In a lab course, students hand in programs, often dozens per lab. EmptyDiff takes these submissions and runs the tests that the lecturers wrote for the lab right away. Students see at once what is right and what is not, and can submit again (up to a configured number of attempts; the default is 7). Lecturers see all submissions and a credit list.

The automatic tests do not replace reading the code. They take the routine check off the supervisors.

For students

  1. Log in: students enter their institution's mail address and receive a one-time code by mail. There are no passwords.
  2. Upload: for each lab they upload the required files. Only files with the given names are accepted. After the deadline submissions are still possible and are marked as late.
  3. Check: the submission runs in a sandbox without network and with limits for time and memory, one at a time.
  4. Report: after a few seconds the result is there: a tick or a cross for every check, with a hint.

For lecturers

Everything is done in the browser: create courses and labs, set the deadline and the required files, write the testbench, make the lab visible to students. New labs start hidden. Lecturers see all labs and can submit like students to try out the testbench.

A testbench is a few lines with check(...) and check_close(...). The verdict never comes from what the student's program prints, but from a results file that only these two functions write. A submission passes if there is at least one check, all checks pass and the testbench runs to the end. 

x = addone(1);
check(x == 2, 'addone(1) returns 2', 'addone(1) does not return 2');
check_close(addone([1 2]), [2 3], 1e-12, 'vectors work', 'vectors are wrong');

Every lab has a list of its submissions. There you can read the code, download a submission as a ZIP, check it again after fixing the testbench, or delete it.

The credit list shows, for each student and lab, the result of the last submission, and can be downloaded as CSV.

There is also: cloning a course for the next semester, backing up and restoring the labs or everything, and a privacy statement that is generated from the configuration. The interface is available in German and English.

Technology and limits

  • Python with Flask behind Apache (mod_wsgi), SQLite as the database, one configuration file. Only packages of the distribution are used: no pip, no Docker, no Node.
  • Submissions run in a bubblewrap sandbox without network, with limits for CPU, memory, processes and output, and strictly one after the other.
  • Data are deleted automatically after a configurable period (default 730 days). There are no trackers and no external resources.
  • Everything that depends on the programming language lives in one adapter per language. Today there is only Octave/MATLAB.
  • The student's code and the testbench run in the same Octave process. A deliberate attack on the check is hindered, but not impossible.
  • Because checks run one after the other, the system is meant for small to medium courses. On a Raspberry Pi 4, 200 simultaneous submissions of a simple task were checked after about a minute. Labs with plots, real mail delivery and TLS have not been tried there yet.
  • There are no automatic backups. Lecturers download them in the web interface.

Installation

Requirements

  • A Linux server with root access and apt. Debian or Ubuntu are recommended; so far it is tested only with Debian 13. On Ubuntu you need Python 3.11 or newer (Ubuntu 24.04 and later).
  • A DNS name for the server and ports 80 and 443 reachable from the internet for the certificate. For closed networks there are two alternatives: plain HTTP, or running behind a reverse proxy (see below).
  • An SMTP server through which the one-time codes are sent.
  • Unprivileged user namespaces in the kernel (the Debian default; on Ubuntu 24.04 AppArmor can restrict them), which bubblewrap needs. The self-test of install.sh shows whether the sandbox works.

Dependencies (packages of the distribution, installed by install.sh)

  • apache2 and libapache2-mod-wsgi-py3 (certificates via the included mod_md)
  • python3 (3.11 or newer) and python3-flask; the rest of the code uses only the standard library
  • bubblewrap and util-linux (for prlimit)
  • for Octave/MATLAB: octave, plus gnuplot-nox and fonts-freefont-otf so that plots work without a display

Steps

sudo apt-get install -y git
sudo git clone https://github.com/andreas-schwenk/EmptyDiff /opt/emptydiff
cd /opt/emptydiff
sudo ./install.sh --accept-acme-terms

On the first run the script creates the template /etc/emptydiff/config.toml and stops. This one configuration file holds the server name, the allowed mail domains, the admins, the mail server and the details for the privacy statement. Then run the script again: 

sudo nano /etc/emptydiff/config.toml
sudo ./install.sh --accept-acme-terms

The script installs the packages, creates the user emptydiff, generates the files for Apache and systemd, checks the sandbox and starts the services. An update is the same call after git pull.

Without a public DNS name there are two ways: base_url with http:// for a closed test network (codes and sessions are then unencrypted), or running behind a reverse proxy that ends TLS and offers the system under a path of its site. Both are described in INSTALL.md, together with operation, updates and notes on the Raspberry Pi.
